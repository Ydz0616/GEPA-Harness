### getsentry/responses URL matching algorithm

For questions about how `BaseResponse` matches URLs across scheme, host, path, query, and regex patterns:

- String URLs are normalized at registration by `_ensure_url_default_path`, which changes an empty path to `"/"`. String URLs are exact path matches, never prefix matches.
- `_should_match_querystring` chooses query mode: explicit `match_querystring=True/False` wins; regex URLs default to `False` for backward compatibility; otherwise query matching is `bool(urlparse(self.url).query)`, so a string URL that literally contains `?...` automatically enables strict query matching.
- Lenient string matching uses `_get_url_and_path`, which compares `scheme`, `netloc` (including port), and `path`, ignoring query and fragment. `http` ≠ `https`; `example.com` ≠ `example.com:8080`; `/foo` ≠ `/foo/`.
- Strict query matching uses `_url_matches_strict`: compare `url_parsed[:3]` (scheme, netloc, path), then compare `sorted(parse_qsl(query))` lists. Query parameter order is ignored, percent-decoding and `+`-as-space are normalized, repeated parameters are preserved as separate tuples, and extra request parameters fail the match.
- Regex URLs bypass component logic and use `Pattern.match(other)` against the full prepared request URL, including query string. This is a prefix match (`re.match` semantics), not a full match; users should anchor with `$` or `\Z` when needed. `match_querystring` and `_get_url_and_path` are irrelevant for regexes.
- Unicode URL handling lives in `_clean_unicode`: non-ASCII domain labels become IDNA punycode, and non-ASCII path/query characters are percent-quoted. Be aware of quirks: the guard is `ord(char) > 128` rather than `>= 128`, and an `isinstance(url.encode("utf8"), six.string_types)` check is a Python-2 leftover.
- Richer query matching belongs in `responses.matchers`: `query_string_matcher` compares sorted parsed query pairs; `query_param_matcher` compares a dict produced by `_parse_request_params`; `fragment_identifier_matcher` inspects the fragment.

### Pint registry architecture

When the question is about Pint’s hierarchical registry design:

- Pint’s registry is split into five capability classes:
  - `BaseRegistry`
  - `NonMultiplicativeRegistry(BaseRegistry)`
  - `ContextRegistry(BaseRegistry)`
  - `SystemRegistry(BaseRegistry)`
  - `UnitRegistry(SystemRegistry, ContextRegistry, NonMultiplicativeRegistry)`
- The MRO is effectively:
  `UnitRegistry → SystemRegistry → ContextRegistry → NonMultiplicativeRegistry → BaseRegistry`.
- Support/plumbing classes include `RegistryMeta`, `RegistryCache`, `ContextCacheOverlay`, `LazyRegistry`, and `ApplicationRegistry`; these are not separate capability tiers.
- `BaseRegistry` handles units, prefixes, dimensions, definition-file parsing, `parse_expression`, `wraps` / `check`, and `define`. Its conversion contract is multiplicative: `_convert` checks dimensionality, then uses `_get_root_units(src / dst)`. Its `_define` docstring says it defines only multiplicative units, converting other types to `delta_` units.
- `NonMultiplicativeRegistry` adds `default_as_delta` and `autoconvert_offset_to_baseunit`; overrides `_parse_units`, `_define`, and `_convert`; and uses `_validate_and_extract` to enforce “at most one offset unit per dimension, exponent 1.”
- `ContextRegistry` adds `@context` parsing, `enable_contexts` / `disable_contexts` / `context()` / `with_context`, turns `_units` into a `ChainMap`, keeps per-context-chain `RegistryCache` variants, and applies context transforms before delegating to `super()._convert`.
- `SystemRegistry` adds `@group` / `@system` parsing, `get_group` / `get_system`, `default_system` (whose setter invalidates `_base_units_cache`), and distinguishes base units from root units.
- `UnitRegistry` is primarily the constructor surface and public API; it forwards options up the MRO and adds methods such as `pi_theorem`, `setup_matplotlib`, `wraps`, and `check`.
- Pint’s changelog states the intent: “Refactored the Registry in multiple classes for better separation of concerns and clarity” (`CHANGES`, section `0.8 (2017-04-16)` @ `5bdf010`).
- The design rationale is orthogonal concerns and delegation: each layer overrides only the hooks it needs and calls `super()`. `RegistryMeta` calls `_after_init()` after construction so definition loading and cache building can happen after all MRO layers have initialized. `_register_parsers` lets each layer register its own definition-file directives such as `@defaults`, `@context`, `@group`, and `@system`.
- The trade-off is MRO subtlety: subclasses must cooperate with `super()`, and behavior depends on linearization order. To add a capability, subclass the specific layer or mix the capability classes and override a single hook such as `_convert`, `_parse_units`, `_define`, `_get_compatible_units`, or `_register_parsers`.
- The application registry deliberately uses composition instead of this inheritance hierarchy: `ApplicationRegistry` is a wrapper with `__slots__ = ["_registry"]` and forwarding methods, introduced in 0.18 as “Convert the application registry to a wrapper object (Issue #1365).”

- `load_definitions()` normalizes inputs:
  - If `is_resource`: `importlib.resources.read_binary(__package__, file)`, decode UTF-8, wrap in `StringIO`, and recurse.
  - Else: `open(file, encoding="utf-8")` and recurse.
  - `RedefinitionError` / `DefinitionSyntaxError` get `.filename` attached; other exceptions become `ValueError("While opening ...")`.
- Resource paths resolve only inside the installed `pint` package. External paths use normal filesystem resolution.

  - For resources: `path = line[7:].strip()`.
  - For external files: resolve relative to `os.path.dirname(file.name)` or `os.getcwd()` if no file handle is available, then join with `os.path.normpath(...)`.
  - `is_resource` is propagated to the nested load.
- `SourceIterator` strips comments with `line.split("#", 1)[0].strip()`, skips blank/comment-only lines, and tracks 1-based line numbers. `BlockIterator` handles block directives (`@defaults`, `@context`, `@group`, `@system`), stops at `@end`, and raises `DefinitionSyntaxError("cannot nest @ directives")` if another `@` appears inside.
- Dispatch:

- Caching has three distinct layers:

It collects dependencies from `_units`, uses `solve_dependencies()` to yield units in topological order, raises `ValueError("Cyclic dependencies exist…")` on cycles, and caches `root_units`, `dimensionality`, `dimensional_equivalents`, and `parse_unit`.   3. **Per-context overlay:** `ContextRegistry` keeps `_units` as a `ChainMap` and `_caches` keyed by the active context chain. `_build_cache()` stores the base cache at `self._caches[()]`. `_switch_context_cache_and_units()` removes prior overlays, reuses the base cache when no redefinitions are active, and otherwise creates a `ContextCacheOverlay` that shares `dimensional_equivalents`, `dimensionality`, and `parse_unit` with the base cache but begins with empty `root_units`. - Practical consequences:
  - Caches are built once at construction. Calling `load_definitions()` or `define()` later does not invalidate `_cache.root_units`, `dimensionality`, or `parse_unit`; rebuild with `_build_cache()`.

### `responses` decorator and dynamic wrapper generation

When the question is about how `getsentry/responses` implements the decorator pattern while preserving function signatures:

- `responses` does not hand-write a generic `wrapper(*args, **kwargs)`.
- `RequestsMock.activate()` delegates to `get_wrapped()`, which synthesizes wrapper source code from the decorated function’s signature and `exec`s it in a namespace containing `func` and the mock instance.
- Template at approximately `responses/__init__.py:152–156` @ `3e02994`:
  ```python
  _wrapper_template = """\
  def wrapper%(wrapper_args)s:
      with responses:
          return func%(func_args)s
  """
  ```
- `get_wrapped()` is approximately lines 159–203. It builds `wrapper_args` and `func_args`, calls `six.exec_`, retrieves the generated `wrapper`, and applies `functools.update_wrapper(wrapper, func)`.
- `wrapper_args` keeps defaults so the wrapper is callable like the original. `func_args` drops defaults and annotations because a call expression cannot contain `name=default`.
- On Python 3, the strings come from `inspect.signature(func)`; parameter annotations are removed with `param.replace(annotation=...)`, defaults are preserved for the definition side, and the return annotation is cleared. On Python 2, the same idea uses `inspect.getargspec` + `inspect.formatargspec`.
- Escape hatch: if `hasattr(func, "__wrapped__")`, the wrapper parameters fall back to `*args, **kwargs`. This is because an already-wrapped function’s visible signature may not describe the arguments it actually receives; the comment names `unittest.mock.patch` as an example.
- The call chain is:
  `@responses.activate` → module-level alias `activate` bound to the singleton `RequestsMock` instance → `RequestsMock.activate(func)` → `get_wrapped(func, self)` → generated wrapper → at call time `RequestsMock.__enter__` → `start()` → `__exit__` → `stop()`.
- Interception happens through `with responses:` in the generated wrapper. `RequestsMock.__enter__` calls `start()`, which patches `requests.adapters.HTTPAdapter.send` via `std_mock.patch(..., new=self.unbound_on_send)`. `_on_request` matches the prepared request, appends a `Call` to `self.calls`, and returns an in-memory `HTTPResponse`, raises `ConnectionError` for an unmatched URL, or defers to the captured `_real_send` when passthrough prefixes match. `__exit__` calls `stop(allow_assert=success)`, restores the original `send`, asserts all registered requests were fired on clean exit, then resets the mock.
- Why generate code instead of using `*args, **kwargs`: preserving the argspec lets pytest and similar tools continue to use fixture injection. A generic wrapper would hide the original parameter names, so fixtures would not be injected.
- Practical consequences:
  - Stacking `@responses.activate` or decorating a function that already has `__wrapped__` switches to the `*args, **kwargs` fallback.
  - `inspect.signature(decorated)` still reports the original parameters via `__wrapped__`.
  - Keyword-only parameters, `*args` / `**kwargs`, and positional-only parameters survive on Python 3 because `str(inspect.Signature)` renders them.
  - Generated source is evaluated once per decoration, not per call.
- The type stub agrees with the runtime identity: `_Activate` is a `Protocol` with `__call__(self, func: _F) -> _F`, and `activate: _Activate` in `responses/__init__.pyi`.

### Pint offset units and variance

When the question asks why Pint raises `OffsetUnitCalculusError` for statistical operations on offset units such as `degC`:

- The relevant registration and unit-output logic is in `pint/numpy_func.py`, especially `get_op_output_unit()`.
- For `variance`, the output unit is computed with an additive dummy expression:
  `((1 * first_input_units + 1 * first_input_units) ** 2).units`
  (approximately lines 195–196 in the referenced commit).
- That addition reaches `_add_sub` in `pint/quantity.py` (approximately line 1018) and raises `OffsetUnitCalculusError` (approximately line 1126) because adding two absolute temperatures is ambiguous: `10 degC + 100 degC` could mean different things depending on whether the values are treated as readings or absolute values.

  and is therefore allowed to produce delta units for differences.
- `docs/nonmult.rst` (approximately lines 94–97) documents the ambiguity.

### Pint Dask Array protocol

When the question is about how `pint.Quantity` implements the Dask Array/collection protocol while preserving units:

- The protocol block is in `pint/quantity.py`, in the `# Dask.array.Array ducking` section near the end of `Quantity`, after `to_timedelta()` and before the module-level `_Quantity = Quantity` alias in the referenced Pint version.
- `__dask_graph__()` delegates to `self._magnitude.__dask_graph__()` when the magnitude is a `dask_array.Array`, otherwise returns `None`. Returning `None` is the protocol signal that a `Quantity` wrapping a scalar or NumPy array is not a Dask collection.
- `__dask_keys__()` delegates to the magnitude’s keys.
- `__dask_optimize__` and `__dask_scheduler__` are exposed as properties returning `dask_array.Array.__dask_optimize__` / `dask_array.Array.__dask_scheduler__`, so Pint uses Dask’s normal optimization and scheduler behavior.
- `__dask_tokenize__()` returns `(Quantity, tokenize(self._magnitude), self.units)`. This makes quantities with equal magnitude graphs but different units distinct collections and avoids collisions in caches/shared graphs. It deliberately uses the module-level `Quantity`, not `type(self)`, because per-registry classes are generated dynamically by `build_quantity_class()` and would destabilize tokens.
- `__dask_postcompute__()` and `__dask_postpersist__()` call the magnitude’s finalizer and return Pint’s `_dask_finalize` with the original units:
  `return self._dask_finalize, (func, args, self.units)`.
- `_dask_finalize(results, func, args, units)` first calls the magnitude’s finalizer, then returns `Quantity(values, units)`. Units never enter the task graph; they are captured at graph-build time and reattached when Dask materializes the result.
- User-facing `compute()`, `persist()`, and `visualize()` methods are decorated with `@check_dask_array`; they pass `self` to `dask.base.compute` / `persist` / `visualize`, which triggers the collection protocol. For non-Dask magnitudes, `check_dask_array` raises `AttributeError`.
- Laziness is preserved by the NumPy interop layer: `__array_ufunc__` / `__array_function__` hand off to `numpy_wrap()` in `pint/numpy_func.py`; Dask arrays participate in NEP-13/NEP-18, so Pint strips units, calls the NumPy function on magnitudes, Dask builds a new lazy array, and Pint reattaches the output unit. `_to_magnitude()` in `pint/compat.py` avoids coercing duck arrays via `np.asarray`. `is_duck_array_type()` recognizes Dask arrays. `Quantity.__getattr__` refuses most `__array_*` attributes to prevent unit stripping.
- In-place operations are Dask-aware: `__iadd__`, `__isub__`, `__imul__`, `__itruediv__`, and `__ipow__` branch on duck-array magnitude and route to internal helpers rather than mutating in place.
- Coverage for Dask integration is in `pint/testsuite/test_dask.py` in the referenced Pint version.

### Pint pickling, unpickling, and registry attachment

When the question is about how unit strings flow through the registry system when unpickling `Quantity` objects created from custom `UnitRegistry` instances:

- `Quantity.__reduce__()` serializes a `UnitsContainer` of canonical unit names, not a raw unit expression, and returns `_unpickle_quantity, (Quantity, self.magnitude, self._units)`. `Quantity.__reduce__`’s docstring states that `UnitRegistry` objects are not pickled and the unpickled object is attached to the application registry.
- `self._units` is a `UnitsContainer`, so expressions such as `"m/s"` and aliases/prefix spellings are not preserved. The class token is the base `Quantity`, because per-registry classes built by `build_quantity_class(registry)` are not picklable.
- Unpickling enters `pint/__init__.py::_unpickle_quantity`, which calls `_unpickle(application_registry.Quantity, *args)`. The ignored `cls` argument means the reconstructed object always uses the application registry’s `Quantity`.
- `_unpickle()` iterates over `UnitsContainer` arguments and calls `application_registry.parse_units(name)` once per unit name. This is required partly because prefixed units may only be defined in the registry after parsing.
- `application_registry` is an `ApplicationRegistry` wrapper around a `LazyRegistry`. The lazy registry initializes a real default `UnitRegistry` on first attribute access and uses `on_redefinition="raise"`. `set_application_registry(registry)` changes the application registry.
- `BaseRegistry.parse_units()` applies preprocessors, then calls `_parse_units()`. `_parse_units()` uses `ParserHelper.from_string()` to tokenize/parse, then `get_name()` / `parse_unit_name()` to resolve names, aliases, prefixes, and suffixes. If a name cannot be resolved, `UndefinedUnitError` is raised.
- When `_unpickle()` later constructs the `Quantity` with a `UnitsContainer`, `Quantity.__new__` takes the container as-is. The `str` branch (`registry.parse_units(...)._units`) is not taken, so the full expression grammar (`parse_expression` → `string_preprocessor` → `tokenizer` → `build_eval_tree`) does not run during ordinary unpickling.
- Practical consequence: custom unit names fail unless `pint.set_application_registry(custom_registry)` is called before unpickling. With multiprocessing, do this in the worker initializer: `fork` inherits the setting, `spawn` does not. Unit identity is by name, so a registry with the same unit name but a different definition silently changes meaning. Aliases and pretty spellings are lost on the way out.

Pint registry architecture
- Pint's registry is split into five capability classes:
  BaseRegistry
  NonMultiplicativeRegistry(BaseRegistry)
  ContextRegistry(BaseRegistry)
  SystemRegistry(BaseRegistry)
  UnitRegistry(SystemRegistry, ContextRegistry, NonMultiplicativeRegistry)
- The MRO is effectively:
  UnitRegistry -> SystemRegistry -> ContextRegistry -> NonMultiplicativeRegistry -> BaseRegistry.
- Support/plumbing classes include RegistryMeta, RegistryCache, ContextCacheOverlay, LazyRegistry, and ApplicationRegistry; these are not separate capability tiers.
- BaseRegistry handles units, prefixes, dimensions, definition-file parsing, parse_expression, wraps/check, and define. Its conversion contract is multiplicative: _convert checks dimensionality, then uses _get_root_units(src / dst). Its _define docstring says it defines only multiplicative units, converting other types to delta_ units.
- NonMultiplicativeRegistry adds default_as_delta and autoconvert_offset_to_baseunit; overrides _parse_units, _define, and _convert; and uses _validate_and_extract to enforce "at most one offset unit per dimension, exponent 1."
- ContextRegistry adds @context parsing, enable_contexts / disable_contexts / context() / with_context, turns _units into a ChainMap, keeps per-context-chain RegistryCache variants, and applies context transforms before delegating to super()._convert.
- SystemRegistry adds @group / @system parsing, get_group / get_system, default_system (whose setter invalidates _base_units_cache), and distinguishes base units from root units.
- UnitRegistry is primarily the constructor surface and public API; it forwards options up the MRO and adds methods such as pi_theorem, setup_matplotlib, wraps, and check.
- Pint's changelog states the intent: "Refactored the Registry in multiple classes for better separation of concerns and clarity" (CHANGES, section 0.8 (2017-04-16) @ 5bdf010).
- The design rationale is orthogonal concerns and delegation: each layer overrides only the hooks it needs and calls super(). RegistryMeta calls _after_init() after construction so definition loading and cache building can happen after all MRO layers have initialized. _register_parsers lets each layer register its own definition-file directives such as @defaults, @context, @group, and @system.
- The trade-off is MRO subtlety: subclasses must cooperate with super(), and behavior depends on linearization order. To add a capability, subclass the specific layer or mix the capability classes and override a single hook such as _convert, _parse_units, _define, _get_compatible_units, or _register_parsers.
- The application registry deliberately uses composition instead of this inheritance hierarchy: ApplicationRegistry is a wrapper with __slots__ = ["_registry"] and forwarding methods, introduced in 0.18 as "Convert the application registry to a wrapper object (Issue #1365)."

- Entry point: BaseRegistry.load_definitions(file, is_resource=False) in pint/registry.py.
- BaseRegistry._after_init() does the loading and cache build:

- Resource paths resolve only inside the installed pint package. External paths use normal filesystem resolution.

  For resources: path = line[7:].strip().
  For external files: resolve relative to os.path.dirname(file.name) or os.getcwd() if no file handle is available, then join with os.path.normpath(...).

- Template at approximately responses/__init__.py:152-156 @ 3e02994:

  def wrapper%(wrapper_args)s:
      with responses:

  """
- get_wrapped() is approximately lines 159-203. It builds wrapper_args and func_args, calls six.exec_, retrieves the generated wrapper, and applies functools.update_wrapper(wrapper, func).

- Practical consequences:
  Stacking @responses.activate or decorating a function that already has __wrapped__ switches to the *args, **kwargs fallback.

getsentry/responses header merging and content-type conflicts
- The header merging logic that causes content-type conflicts is implemented in BaseResponse.get_headers() in responses/__init__.py, approximately lines 338-344 @ 3e02994.
- The method creates an HTTPHeaderDict instance and follows a two-step process:
  If self.content_type is not None, it sets headers["Content-Type"] = self.content_type, approximately lines 340-341.
  Then it calls headers.extend(self.headers) to merge in user-provided headers, approximately lines 342-343.
- The root cause is HTTPHeaderDict.extend() behavior: it concatenates duplicate header values with commas rather than overriding them. The comment "Duplicate headers are legal" at approximately line 339 documents the intent.
- When both the content_type parameter and a Content-Type key in the headers dictionary are specified, this can result in malformed Content-Type headers such as "application/json, application/json" for identical values or "application/json, text/plain" for conflicting values.
- Response.__init__ resolves content_type before get_headers() runs. If json is not None, it defaults to application/json. If content_type is UNSET, it defaults to text/plain; charset=utf-8 for unicode bodies with non-ASCII, otherwise text/plain. content_type is None only if explicitly passed as None.
- Call chain:
  responses.add(method, url, body, adding_headers=..., **kwargs) builds a Response(method=..., url=..., body=..., **kwargs); adding_headers maps into the headers kwarg. Passing a BaseResponse instance short-circuits this.
  RequestsMock._on_request() -> adapter.build_response(request, match.get_response(request)).
  Response.get_response() calls headers = self.get_headers() and returns HTTPResponse(status=..., body=body, headers=headers, original_response=OriginalResponseShim(headers), ...).
  requests.adapters.HTTPAdapter.build_response wraps headers into the Response object the test sees.
- The codebase demonstrates awareness of this issue in CallbackResponse.get_response(), approximately lines 469-483. It explicitly checks whether callback-provided headers contain Content-Type, handling both dict and list formats, and if so removes the pre-existing Content-Type header with headers.pop("Content-Type", None) before extending with callback-provided headers. The plain Response.get_headers() path lacks this de-duplication.
- Practical workarounds at this commit:
  Do not pass both. Let content_type drive it, or put Content-Type only in headers together with content_type=None.
  If subclassing BaseResponse, override get_headers() and use replacement semantics such as headers.update(self.headers), or pop Content-Type from the incoming mapping before extending.

  - `UnitRegistry(SystemRegistry, ContextRegistry, NonMultiplicativeRegistry)`
- The MRO is effectively:
  `UnitRegistry → SystemRegistry → ContextRegistry → NonMultiplicativeRegistry → BaseRegistry`.
- Support/plumbing classes include `RegistryMeta`, `RegistryCache`, `ContextCacheOverlay`, `LazyRegistry`, and `ApplicationRegistry`; these are not separate capability tiers.
- `BaseRegistry` handles units, prefixes, dimensions, definition-file parsing, `parse_expression`, `wraps` / `check`, and `define`. Its conversion contract is multiplicative: `_convert` checks dimensionality, then uses `_get_root_units(src / dst)`. Its `_define` docstring says it defines only multiplicative units, converting other types to `delta_` units.
- `NonMultiplicativeRegistry` adds `default_as_delta` and `autoconvert_offset_to_baseunit`; overrides `_parse_units`, `_define`, and `_convert`; and uses `_validate_and_extract` to enforce “at most one offset unit per dimension, exponent 1.”
- `ContextRegistry` adds `@context` parsing, `enable_contexts` / `disable_contexts` / `context()` / `with_context`, turns `_units` into a `ChainMap`, keeps per-context-chain `RegistryCache` variants, and applies context transforms before delegating to `super()._convert`.
- `SystemRegistry` adds `@group` / `@system` parsing, `get_group` / `get_system`, `default_system` (whose setter invalidates `_base_units_cache`), and distinguishes base units from root units.
- `UnitRegistry` is primarily the constructor surface and public API; it forwards options up the MRO and adds methods such as `pi_theorem`, `setup_matplotlib`, `wraps`, and `check`.
- Pint’s changelog states the intent: “Refactored the Registry in multiple classes for better separation of concerns and clarity” (`CHANGES`, section `0.8 (2017-04-16)` @ `5bdf010`).
- The design rationale is orthogonal concerns and delegation: each layer overrides only the hooks it needs and calls `super()`. `RegistryMeta` calls `_after_init()` after construction so definition loading and cache building can happen after all MRO layers have initialized. `_register_parsers` lets each layer register its own definition-file directives such as `@defaults`, `@context`, `@group`, and `@system`.
- The trade-off is MRO subtlety: subclasses must cooperate with `super()`, and behavior depends on linearization order. To add a capability, subclass the specific layer or mix the capability classes and override a single hook such as `_convert`, `_parse_units`, `_define`, `_get_compatible_units`, or `_register_parsers`.
- The application registry deliberately uses composition instead of this inheritance hierarchy: `ApplicationRegistry` is a wrapper with `__slots__ = ["_registry"]` and forwarding methods, introduced in 0.18 as “Convert the application registry to a wrapper object (Issue #1365).”

### Pint definition loading and caching

When the question is about `UnitRegistry` file-based definition loading, `@import`, or caching:

- Entry point: `BaseRegistry.load_definitions(file, is_resource=False)` in `pint/registry.py`.
- `BaseRegistry._after_init()` does the loading and cache build:
  - `filename == ""` → `load_definitions("default_en.txt", True)` for the packaged resource.
  - `filename is not None` → `load_definitions(self._filename)` for an external file.
  - Then `_build_cache()` and `_initialized = True`.
- `load_definitions()` normalizes inputs:
  - If `is_resource`: `importlib.resources.read_binary(__package__, file)`, decode UTF-8, wrap in `StringIO`, and recurse.
  - Else: `open(file, encoding="utf-8")` and recurse.
  - `RedefinitionError` / `DefinitionSyntaxError` get `.filename` attached; other exceptions become `ValueError("While opening ...")`.
- Resource paths resolve only inside the installed `pint` package. External paths use normal filesystem resolution.
- `@import` handling:
  - For resources: `path = line[7:].strip()`.
  - For external files: resolve relative to `os.path.dirname(file.name)` or `os.getcwd()` if no file handle is available, then join with `os.path.normpath(...)`.
  - `is_resource` is propagated to the nested load.
- `SourceIterator` strips comments with `line.split("#", 1)[0].strip()`, skips blank/comment-only lines, and tracks 1-based line numbers. `BlockIterator` handles block directives (`@defaults`, `@context`, `@group`, `@system`), stops at `@end`, and raises `DefinitionSyntaxError("cannot nest @ directives")` if another `@` appears inside.
- Dispatch:
  - `@directive` lines use `_BLOCK_RE.split(line)` and `_parsers`; unknown directives raise `DefinitionSyntaxError`.
  - Plain definition lines use `self.define(Definition.from_string(line, self.non_int_type))`. `DefinitionSyntaxError` gets `.lineno`; other exceptions are logged and loading continues. Malformed plain definition lines are non-fatal; malformed directive blocks abort loading.
- `_parsers` is a class-level dict populated by `_register_parsers()` / `_register_parser(prefix, func)` during `__init__`, allowing each registry layer to add syntax.
- Caching has three distinct layers:
  1. Derived-value cache: `RegistryCache` rebuilt by `_build_cache()`. It collects dependencies from `_units`, uses `solve_dependencies()` to yield units in topological order, raises `ValueError("Cyclic dependencies exist…")` on cycles, and caches `root_units`, `dimensionality`, `dimensional_equivalents`, and `parse_unit`. Per-unit resolution failures are logged.
  2. Parsing caches: `ParserHelper.from_string` is decorated `@classmethod @lru_cache()` in `pint/util.py`; `pattern_to_regex` in `pint/registry.py` is `@functools.lru_cache()`. These caches are process-global and keyed by text plus type information, so they are shared across registries/contexts.
  3. Per-context overlay: `ContextRegistry` keeps `_units` as a `ChainMap` and `_caches` keyed by the active context chain. `_build_cache()` stores the base cache at `self._caches[()]`. `_switch_context_cache_and_units()` removes prior overlays, reuses the base cache when no redefinitions are active, and otherwise creates a `ContextCacheOverlay` that shares `dimensional_equivalents`, `dimensionality`, and `parse_unit` with the base cache but begins with empty `root_units`. Context redefinitions land in `_units.maps[0]` while `on_redefinition` is temporarily `"ignore"`.
- `BaseRegistry._parse_units` has a guard: a cached `parse_unit` entry is trusted only if `input_string in self._units`, fixing issue #1097 where a unit defined under one context poisoned the parse cache for another.
- Practical consequences:
  - Caches are built once at construction. Calling `load_definitions()` or `define()` later does not invalidate `_cache.root_units`, `dimensionality`, or `parse_unit`; rebuild with `_build_cache()`.
  - `UnitRegistry(None)` is legal and yields an empty registry; caches still exist.
  - `is_resource` is not auto-detected. `load_definitions("default_en.txt")` looks for a file in the CWD unless `is_resource=True`.
  - Relative `@import` depends on having a real file handle; in-memory line streams fall back to `os.getcwd()`.

### `responses` decorator and dynamic wrapper generation

When the question is about how `getsentry/responses` implements the decorator pattern while preserving function signatures:

- `responses` does not hand-write a generic `wrapper(*args, **kwargs)`.
- `RequestsMock.activate()` delegates to `get_wrapped()`, which synthesizes wrapper source code from the decorated function’s signature and `exec`s it in a namespace containing `func` and the mock instance.
- Template at approximately `responses/__init__.py:152–156` @ `3e02994`:
  ```
  _wrapper_template = """\
  def wrapper%(wrapper_args)s:
      with responses:
          return func%(func_args)s
  """
  ```
- `get_wrapped()` is approximately lines 159–203. It builds `wrapper_args` and `func_args`, calls `six.exec_`, retrieves the generated `wrapper`, and applies `functools.update_wrapper(wrapper, func)`.
- `wrapper_args` keeps defaults so the wrapper is callable like the original. `func_args` drops defaults and annotations because a call expression cannot contain `name=default`.
- On Python 3, the strings come from `inspect.signature(func)`; parameter annotations are removed with `param.replace(annotation=...)`, defaults are preserved for the definition side, and the return annotation is cleared. On Python 2, the same idea uses `inspect.getargspec` + `inspect.formatargspec`.
- Escape hatch: if `hasattr(func, "__wrapped__")`, the wrapper parameters fall back to `*args, **kwargs`. This is because an already-wrapped function’s visible signature may not describe the arguments it actually receives; the comment names `unittest.mock.patch` as an example.
- The call chain is:
  `@responses.activate` → module-level alias `activate` bound to the singleton `RequestsMock` instance → `RequestsMock.activate(func)` → `get_wrapped(func, self)` → generated wrapper → at call time `RequestsMock.__enter__` → `start()` → `__exit__` → `stop()`.
- Interception happens through `with responses:` in the generated wrapper. `RequestsMock.__enter__` calls `start()`, which patches `requests.adapters.HTTPAdapter.send` via `std_mock.patch(..., new=self.unbound_on_send)`. `_on_request` matches the prepared request, appends a `Call` to `self.calls`, and returns an in-memory `HTTPResponse`, raises `ConnectionError` for an unmatched URL, or defers to the captured `_real_send` when passthrough prefixes match. `__exit__` calls `stop(allow_assert=success)`, restores the original `send`, asserts all registered requests were fired on clean exit, then resets the mock.
- Why generate code instead of using `*args, **kwargs`: preserving the argspec lets pytest and similar tools continue to use fixture injection. A generic wrapper would hide the original parameter names, so fixtures would not be injected.
- Practical consequences:
  - Stacking `@responses.activate` or decorating a function that already has `__wrapped__` switches to the `*args, **kwargs` fallback.
  - `inspect.signature(decorated)` still reports the original parameters via `__wrapped__`.
  - Keyword-only parameters, `*args` / `**kwargs`, and positional-only parameters survive on Python 3 because `str(inspect.Signature)` renders them.
  - Generated source is evaluated once per decoration, not per call.
- The type stub agrees with the runtime identity: `_Activate` is a `Protocol` with `__call__(self, func: _F) -> _F`, and `activate: _Activate` in `responses/__init__.pyi`.

### `responses` header merging and content-type conflicts @ `3e02994`

When the question asks where header merging causes `content_type` / `Content-Type` conflicts:

- The merge point is `BaseResponse.get_headers()` in `responses/__init__.py` (approximately lines 338–344).
- It creates `HTTPHeaderDict()` with the comment “Duplicate headers are legal”, then:
  - if `self.content_type is not None`, sets `headers["Content-Type"] = self.content_type`;
  - if `self.headers`, calls `headers.extend(self.headers)`.
- `HTTPHeaderDict.extend()` appends values rather than replacing them. Duplicate values for the same case-insensitive header key are later joined with `", "`, so a conflicting `Content-Type` can appear as `text/plain, application/json`.
- `Response.__init__` resolves `content_type` independently of `headers`: `json=` and `content_type` still `UNSET` → `"application/json"`; otherwise `UNSET` → `"text/plain"`, or `"text/plain; charset=utf-8"` for a unicode body containing non-ASCII.
- `CallbackResponse.__init__` also sets a default `content_type="text/plain"`, so the collision is reachable through `add_callback()`.
- `CallbackResponse.get_response()` contains a workaround (approximately lines 469–480, with `headers.extend(r_headers)` around line 483): it checks whether callback-provided headers contain `Content-Type` in either dict or list form and, if so, calls `headers.pop("Content-Type", None)` before extending. `Response.get_response()` has no such mitigation.
- Execution order: `RequestsMock.add()` / `replace()` / `upsert()` constructs `Response(...)` or `CallbackResponse(...)`; at request time `RequestsMock._on_request()` → `_find_match()` → `match.get_response(request)`; `Response.get_response()` calls `self.get_headers()` (the merge); then `HTTPResponse(headers=...)` goes through `HTTPAdapter.build_response()` to `requests.Response.headers`.
- Later history for orientation: PR #487 (fixing issue #483, after this commit) turned the ambiguity into an explicit `RuntimeError` when both `content_type` and `headers["Content-Type"]` are supplied. At `3e02994`, no such guard exists, so the behavior is a silent duplicate.
- Practical guidance: do not pass both; use `content_type="application/json"` or `headers={"Content-Type": "application/json"}`, not both. If inheriting a headers dict, strip the key before constructing the response.

### Pint offset units and variance

When the question asks why Pint raises `OffsetUnitCalculusError` for statistical operations on offset units such as `degC`:

- Relevant registration and unit-output logic is in `pint/numpy_func.py`, especially `get_op_output_unit()`.
- For `variance`, the output unit is computed with an additive dummy expression:
  `((1 * first_input_units + 1 * first_input_units) ** 2).units` (approximately lines 195–196 in `5bdf010`).
- That addition reaches `_add_sub` in `pint/quantity.py` (approximately line 1018) and raises `OffsetUnitCalculusError` (approximately line 1126) because adding two absolute temperatures is ambiguous: `10 degC + 100 degC` could mean different things depending on whether the values are treated as readings or absolute values.
- Contrast with the `"delta"` branch, which uses subtraction `(1 * unit - 1 * unit).units` and is therefore allowed to produce delta units for differences.
- `docs/nonmult.rst` (approximately lines 94–97) documents the ambiguity.
- Auto-converting variance to `delta_degC²` would silently reinterpret absolute readings as intervals. Pint instead refuses to guess and forces the user to convert to kelvin or work explicitly in delta units.
- Test coverage may be in `pint/testsuite/test_numpy_func.py` (approximately lines 172–173 for `get_op_output_unit("variance", ureg.degC)`).

### Pint definition loading and caching

When the question is about `UnitRegistry` file-based definition loading, `@import`, or caching:

- Entry point: `BaseRegistry.load_definitions(file, is_resource=False)` in `pint/registry.py`.
- `BaseRegistry._after_init()` does the loading and cache build:
  - `filename == ""` → `load_definitions("default_en.txt", True)` for the packaged resource.
  - `filename is not None` → `load_definitions(self._filename)` for an external file.
  - Then `_build_cache()` and `_initialized = True`.
- `load_definitions()` normalizes inputs:
  - If `is_resource`: `importlib.resources.read_binary(__package__, file)`, decode UTF-8, wrap in `StringIO`, and recurse.
  - Else: `open(file, encoding="utf-8")` and recurse.
  - `RedefinitionError` / `DefinitionSyntaxError` get `.filename` attached; other exceptions become `ValueError("While opening ...")`.
- Resource paths resolve only inside the installed `pint` package. External paths use normal filesystem resolution.
- `@import` handling:
  - For resources: `path = line[7:].strip()`.
  - For external files: resolve relative to `os.path.dirname(file.name)` or `os.getcwd()` if no file handle is available, then join with `os.path.normpath(...)`.
  - `is_resource` is propagated to the nested load.
- `SourceIterator` strips comments with `line.split("#", 1)[0].strip()`, skips blank/comment-only lines, and tracks 1-based line numbers. `BlockIterator` handles block directives (`@defaults`, `@context`, `@group`, `@system`), stops at `@end`, and raises `DefinitionSyntaxError("cannot nest @ directives")` if another `@` appears inside.
- Dispatch:
  - `@directive` lines use `_BLOCK_RE.split(line)` and `_parsers`; unknown directives raise `DefinitionSyntaxError`.
  - Plain definition lines use `self.define(Definition.from_string(line, self.non_int_type))`. `DefinitionSyntaxError` gets `.lineno`; other exceptions are logged and loading continues. Malformed plain definition lines are non-fatal; malformed directive blocks abort loading.
- `_parsers` is a class-level dict populated by `_register_parsers()` / `_register_parser(prefix, func)` during `__init__`, allowing each registry layer to add syntax.
- Caching has three distinct layers:
  1. **Derived-value cache:** `RegistryCache` rebuilt by `_build_cache()`. It collects dependencies from `_units`, uses `solve_dependencies()` to yield units in topological order, raises `ValueError("Cyclic dependencies exist…")` on cycles, and caches `root_units`, `dimensionality`, `dimensional_equivalents`, and `parse_unit`. Per-unit resolution failures are logged.
  2. **Parsing caches:** `ParserHelper.from_string` is decorated `@classmethod @lru_cache()` in `pint/util.py`; `pattern_to_regex` in `pint/registry.py` is `@functools.lru_cache()`. These caches are process-global and keyed by text plus type information, so they are shared across registries/contexts.
  3. **Per-context overlay:** `ContextRegistry` keeps `_units` as a `ChainMap` and `_caches` keyed by the active context chain. `_build_cache()` stores the base cache at `self._caches[()]`. `_switch_context_cache_and_units()` removes prior overlays, reuses the base cache when no redefinitions are active, and otherwise creates a `ContextCacheOverlay` that shares `dimensional_equivalents`, `dimensionality`, and `parse_unit` with the base cache but begins with empty `root_units`. Context redefinitions land in `_units.maps[0]` while `on_redefinition` is temporarily `"ignore"`.
- `BaseRegistry._parse_units` has a guard: a cached `parse_unit` entry is trusted only if `input_string in self._units`, fixing issue #1097 where a unit defined under one context poisoned the parse cache for another.
- Practical consequences:
  - Caches are built once at construction. Calling `load_definitions()` or `define()` later does not invalidate `_cache.root_units`, `dimensionality`, or `parse_unit`; rebuild with `_build_cache()`.
  - `UnitRegistry(None)` is legal and yields an empty registry; caches still exist.
  - `is_resource` is not auto-detected. `load_definitions("default_en.txt")` looks for a file in the CWD unless `is_resource=True`.
  - Relative `@import` depends on having a real file handle; in-memory line streams fall back to `os.getcwd()`.

### `responses` decorator and dynamic wrapper generation

When the question is about how `getsentry/responses` implements the decorator pattern while preserving function signatures:

- `responses` does not hand-write a generic `wrapper(*args, **kwargs)`.
- `RequestsMock.activate()` delegates to `get_wrapped()`, which synthesizes wrapper source code from the decorated function’s signature and `exec`s it in a namespace containing `func` and the mock instance.
- Template at approximately `responses/__init__.py:152–156` @ `3e02994`:
  ```python
  _wrapper_template = """\
  def wrapper%(wrapper_args)s:
      with responses:
          return func%(func_args)s
  """
  ```
- `get_wrapped()` is approximately lines 159–203. It builds `wrapper_args` and `func_args`, calls `six.exec_`, retrieves the generated `wrapper`, and applies `functools.update_wrapper(wrapper, func)`.
- `wrapper_args` keeps defaults so the wrapper is callable like the original. `func_args` drops defaults and annotations because a call expression cannot contain `name=default`.
- On Python 3, the strings come from `inspect.signature(func)`; parameter annotations are removed with `param.replace(annotation=...)`, defaults are preserved for the definition side, and the return annotation is cleared. On Python 2, the same idea uses `inspect.getargspec` + `inspect.formatargspec`.
- Escape hatch: if `hasattr(func, "__wrapped__")`, the wrapper parameters fall back to `*args, **kwargs`. This is because an already-wrapped function’s visible signature may not describe the arguments it actually receives; the comment names `unittest.mock.patch` as an example.
- The call chain is:
  `@responses.activate` → module-level alias `activate` bound to the singleton `RequestsMock` instance → `RequestsMock.activate(func)` → `get_wrapped(func, self)` → generated wrapper → at call time `RequestsMock.__enter__` → `start()` → `__exit__` → `stop()`.
- Interception happens through `with responses:` in the generated wrapper. `RequestsMock.__enter__` calls `start()`, which patches `requests.adapters.HTTPAdapter.send` via `std_mock.patch(..., new=self.unbound_on_send)`. `_on_request` matches the prepared request, appends a `Call` to `self.calls`, and returns an in-memory `HTTPResponse`, raises `ConnectionError` for an unmatched URL, or defers to the captured `_real_send` when passthrough prefixes match. `__exit__` calls `stop(allow_assert=success)`, restores the original `send`, asserts all registered requests were fired on clean exit, then resets the mock.
- Why generate code instead of using `*args, **kwargs`: preserving the argspec lets pytest and similar tools continue to use fixture injection. A generic wrapper would hide the original parameter names, so fixtures would not be injected.
- Practical consequences:
  - Stacking `@responses.activate` or decorating a function that already has `__wrapped__` switches to the `*args, **kwargs` fallback.
  - `inspect.signature(decorated)` still reports the original parameters via `__wrapped__`.
  - Keyword-only parameters, `*args` / `**kwargs`, and positional-only parameters survive on Python 3 because `str(inspect.Signature)` renders them.
  - Generated source is evaluated once per decoration, not per call.
- The type stub agrees with the runtime identity: `_Activate` is a `Protocol` with `__call__(self, func: _F) -> _F`, and `activate: _Activate` in `responses/__init__.pyi`.

### Pint offset units and variance

### `getsentry/responses` callback validation at `3e02994`

When asked how `responses` implements callback signature validation and type checking for `add_callback`:

- `RequestsMock.add_callback()` (`responses/__init__.py:669–683` at `3e02994`) performs no signature inspection and no runtime type checking. It simply creates a `CallbackResponse` and stores the callback.
- `CallbackResponse.__init__` (`responses/__init__.py:443–456`) stores `self.callback = callback` directly at approximately line 447 before calling `BaseResponse.__init__`.
- Callback execution happens in `CallbackResponse.get_response()` (`responses/__init__.py:458–492`): it calls `self.callback(request)` at approximately line 461, then if the result is an `Exception` it raises it. It unpacks the result as `status, r_headers, body = result` at approximately line 465, and if `body` is an `Exception` it raises it.
- Runtime enforcement is duck typing: a zero-argument or wrong-arity callback raises a plain `TypeError` at request time; a non-3-item return raises `ValueError`/`TypeError` during unpacking.
- The only actual type checking is static, in the shipped stub file `responses/__init__.pyi`:
  - `_AddCallback` Protocol (approximately lines 208–216) types `callback` as `Callable[[PreparedRequest], Union[Exception, Tuple[int, Mapping[str, str], _Body]]]`.
  - `_Body` is `Union[str, BaseException, "Response", BufferedReader, bytes]`.
  - `CallbackResponse.callback` is typed as `Callable[[Any], Any]`.
- `responses/py.typed` is shipped, so mypy/IDE checking validates the callback shape statically. There is no runtime introspection of the callback signature.
- `inspect` is imported in `responses/__init__.py`, but its only relevant use is `get_wrapped()` for the `@responses.activate` decorator; it inspects the decorated test function, not mock callbacks.
- The error path in `RequestsMock._on_request` wraps `match.get_response(request)` in `try: ... except BaseException as response:`, increments `match.call_count`, records the call in `self._calls`, applies `response_callback`, and bare-`raise`s. Thus callback errors surface at request time inside the mocked `send` path, with the call still recorded.
- Practical consequences: mistyped callbacks fail at the first matching request rather than at `add_callback()` registration; callbacks may legally return an `Exception` or an exception body to force a failure; they may not return a `Response` object or a 2-tuple; `status` is not coerced, so a `str` status is passed through to `HTTPResponse`.

### `getsentry/responses` and `assert_all_requests_are_fired` at `3e02994`

When asked why `responses` has different default behavior for `assert_all_requests_are_fired` between context-manager and decorator usage:

- The premise needs a correction: `@responses.activate` is not a separate code path from `with responses:`. Both go through the same `RequestsMock` lifecycle methods and the same `stop()` call.
- `RequestsMock.__init__` (`responses/__init__.py:531` at `3e02994`) has `assert_all_requests_are_fired: bool = True`. A newly constructed `responses.RequestsMock()` therefore defaults to strict checking.
- At module scope (`responses/__init__.py:843`), the library creates `_default_mock = RequestsMock(assert_all_requests_are_fired=False)`. All module-level helpers (`responses.add`, `responses.start`, `responses.stop`, `responses.reset`, `responses.activate`, etc.) delegate to this singleton, including `activate = _default_mock.activate` (approximately line 875).
- `RequestsMock.activate(func)` returns `get_wrapped(func, self)`. `get_wrapped()` generates a wrapper whose body is effectively `with responses: return func(*args)`, so decorator usage executes `__enter__` → body → `__exit__` on the bound instance.
- `RequestsMock.__enter__` calls `self.start()` and returns `self`. `RequestsMock.__exit__` (`responses/__init__.py:692–700`) computes `success = type is None`, calls `self.stop(allow_assert=success)`, then `self.reset()`, and returns `success`.
- `RequestsMock.stop()` (`responses/__init__.py:808–822`) first unpatches the adapter. It returns early if `self.assert_all_requests_are_fired` is false, and also returns early if `allow_assert` is false. Otherwise it computes `not_called = [m for m in self._matches if m.call_count == 0]` and raises `AssertionError` listing the unmatched `(method, url)` pairs.
- Therefore: `@responses.activate` and `responses.start()/stop()` use the lax module singleton (`False`), while `with responses.RequestsMock() as rsps:` uses a fresh instance whose constructor default is strict (`True`). The difference is instance default and lifecycle/isolation, not decorator versus context manager mechanics.
- The shared singleton is process-global and long-lived. `reset()` runs at `__exit__`, but registrations can still outlive a single request sequence in `setUp`/fixture patterns, so strict “every registered response must be consumed” checking on the shared namespace would produce noise and cross-test interference. An explicitly constructed `RequestsMock` gives a clear isolation boundary, so it is safe for it to assert by default.
- Tests confirm the constructor default: `responses/test_responses.py` approximately lines 1025–1027 explicitly verify that `RequestsMock()` defaults to `assert_all_requests_are_fired=True`.
- Important foot-gun: the module-level `assert_all_requests_are_fired` is a plain bool snapshot, not a property. Setting `responses.assert_all_requests_are_fired = True` rebinds a module attribute and does not change the instance. To enable it for the shared namespace, mutate `responses.mock.assert_all_requests_are_fired = True` (or use your own instance).
- The `allow_assert=success` guard is deliberate: when the decorated function or `with` body raises, the “not all requests fired” assertion is skipped so it does not mask the real failure. This applies identically to both usage patterns.
- `_on_request` pops the first matching registration from `self._matches`, and increments `call_count` even when `get_response` raises, so `call_count == 0` means “remaining registered response never consumed,” not strict one-response-one-request accounting.

### responses signature preservation

When the question is about how `responses` preserves decorated function signatures for pytest-style fixture injection:

- The key function is `get_wrapped(func, responses)` in `responses/__init__.py`, around lines 155–203 at commit `3e02994` (verify exact range at the requested commit).
- `activate()` is a thin front end that hands an ordinary function to `get_wrapped()` rather than writing its own generic wrapper.
- `get_wrapped()` synthesizes a new function as source code whose parameter list is copied from the decorated callable, then `exec`s it. The generated wrapper therefore has a real argspec, so pytest’s collection-time fixture discovery sees names such as `self`, `monkeypatch`, and `tmp_path` instead of an opaque `*args, **kwargs`.
- The wrapper template is essentially:
  `def wrapper%(wrapper_args)s:`
  `    with responses:`
  `        return func%(func_args)s`
  It is executed with an eval dict containing `func` and `responses`, then the generated `wrapper` is returned.
- Python 3 branch:
  - `signature = inspect.signature(func)`
  - remove the return annotation with `signature.replace(return_annotation=inspect.Signature.empty)`
  - if `hasattr(func, "__wrapped__")`, replace parameters with `*args, **kwargs` intentionally
  - `wrapper_args = str(signature)` is used in the `def` line
  - for the call side, strip annotations and defaults to build `func_args`
- Python 2 branch:
  - uses `inspect.getargspec` plus `inspect.formatargspec(args, a, kw, defaults)` for the `def`
  - uses `inspect.formatargspec(args, a, kw, None)` for the call args
- Why source generation instead of plain `functools.wraps`:
  - `wraps` copies metadata and sets `__wrapped__`, but the wrapper’s own `__code__` is still `(*args, **kwargs)`.
  - Fixture injection is resolved from the signature at collection time. Any path that reads the function object directly does not follow `__wrapped__` and sees no parameter names, so fixtures fail to inject or pytest errors about unknown arguments.
  - Emitting real source makes signature inspection and call behavior agree: real `co_varnames`, real defaults, and `self` preserved so methods bind normally.
- Costs and traps:
  - String-generated code can raise `SyntaxError` at decoration time for odd signatures.
  - Return annotations are the classic trap: leaving `return_annotation` in can generate a call like `return func(self) -> None`, which is invalid syntax. That is why the Python 3 branch strips the return annotation before building `func_args`.
  - Decorator order matters. If the function reaching `get_wrapped` already has `__wrapped__` (for example, `@responses.activate` placed above `@mock.patch(...)`), responses deliberately falls back to `*args, **kwargs`; signature preservation is skipped and fixture injection can stop. Put `@responses.activate` closest to the `def` and `@mock.patch` above it.
  - Defaults are resolved by the generated wrapper, not the original call. The generated `def` carries the real defaults, so calling `wrapper()` fills them and then invokes `func(a, b)` positionally; the call-side signature therefore has defaults and annotations removed.
  - `self` works because the generated `def` includes `self`; pytest injects fixtures for the remaining names.
  - `update_wrapper` preserves metadata such as `__name__` and `__doc__`.
